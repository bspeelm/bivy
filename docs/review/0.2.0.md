# 0.2.0

The first release where the program grew rather than the machinery around it.
A playlist, a run through it, and a list that scrolls when you scroll and
stops when you stop.

## What changed since 0.1.5

**A playlist.** `s` puts the row under the cursor on it, `:playlist` is that
list oldest first, and `p` plays down it — starting the next video when one
reaches its end, stopping on anything that is not a clean finish so closing a
window is how you leave. Watching something to the end takes it off the list
wherever it was played from, and `m` says the same thing by hand: marks it
watched, takes it off.

A row is stored rather than pointed at. A search result belongs to no feed,
and a feed has rolled past its own oldest entries by the time anyone comes
back, so the list keeps what the row was when it was added.

**Scrolling that stops when you do.** The loop drew a frame per keypress and
every frame fetched a thumbnail on the main loop, so a held key queued faster
than it drained and the cursor travelled on after the key came up. Everything
already waiting is handled before drawing now. A missing thumbnail no longer
costs a second of backoff either: the first address 404s whenever the larger
size was never made — the whole reason a second address exists — and that 404
was being retried three times before the fallback was tried at all.

**A wheel notch is one row.** bivy asked for no mouse reporting, so the
terminal was answering each notch with three arrow keys of its own. It asks
now. The cost, stated in the README: click-drag no longer selects text in
bivy's window, and shift-drag does.

**`M` can load more.** The ceiling on a query was thirty, which was also the
size of a page, so the first request already reached it and every later one was
clamped back to the same rows. It could not add a row in any view, in any
version. There is no ceiling now: the service stops yielding a search around
six hundred rows, well inside the time any one query is given, and the caller
already stops when a page adds nothing.

**The window opens smaller than the screen and keeps the size it is given.**
mpv fits its window to each video by default, so a window sized by hand was
resized by whatever played next — and the session's first video sized it to
itself, which for anything at the screen's resolution meant filling it.

## What was checked

| check | result |
|---|---|
| `make check` on Linux and macOS, in CI | green |
| `make dist-reproducible` | two builds, byte-identical |
| playback by hand, against the live service | played to its end, `end-file eof` |
| the live player accepts the flag set | green, including the two new options |
| the weekly outdated check | ran, found nothing, stayed quiet |

Three of this release's changes were measured against the real thing rather
than reasoned about, and two of those measurements corrected a decision:

| what was measured | what it said |
|---|---|
| a 4K video on a 1920x1080 screen | window 1920x1080 without a bound, 1344x756 with one |
| a session's second video, 320x240 then 3840x2160 | window followed the video, until told not to |
| `ytsearch300` / `ytsearch1000` against the live service | 300 rows in 9s, 585 in 20s — the service stops, not bivy |

The paging measurement is why there is no ceiling: the number that was there
had been picked rather than found, and once asked, the service turned out to
have one of its own.

## What was not checked

- **Nobody has launched bivy on macOS.** The suite and the scheduled
  integration run both execute there; no person has started the program on a
  Mac. PLAN.md §12 asks for that pass and it is still outstanding.
- **Stream resolution is not covered by CI and cannot be** (ADR-015).
- **The mouse wheel has been tested by its decoder and not by a hand.** No
  test can press a wheel, so what is verified is that bivy asks for mouse
  reporting and reads the report correctly.
- **The window bound was measured on one screen.** 70% of 1920x1080 is a
  comfortable window; nobody has tried it on a 4K panel or a very small one.
- **Thumbnails have no automated test that draws pixels**, and the terminal
  they were confirmed on does not answer the cell-size query, so they are
  drawn at an assumed cell size.
- **No security review by anyone outside this project.**
- **Nothing has been tested at scale** — a handful of followed channels, and a
  playlist of two.

## Known outstanding

- **A playlist was lost during this release's development.** The list was
  briefly called a queue; the rename shipped; bivy started, read a file whose
  key it no longer recognised, and wrote it back without it two seconds later.
  Nothing said so. `TestTheStateFileKeepsItsShape` now pins the names on disk
  so a rename fails a test rather than a user, but the data was not
  recoverable and no migration was added — the old key existed for ten minutes
  and was never released.
- Search still holds the loop for as long as the extractor takes, so nothing
  responds while one runs. That is why the hint line says nothing while it
  does.
- The window size is not remembered between sessions.
- The visitor identifier works around someone else's anti-bot measure and they
  get a vote (ADR-016).
- Playback from inside a container needs the host's mpv on the PATH.
- PLAN.md §13 still lists the open decisions.
