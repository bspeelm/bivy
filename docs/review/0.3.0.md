# 0.3.0

The release where bivy stopped behaving like something worth blocking.

An address running bivy was refused by the service for every client on it,
browsers included. Three things bivy did made its request pattern worse than
its traffic warranted, and all three were on paths nobody watched: the launch,
the draw, and the retry.

## What changed since 0.2.0

**bivy stops when the service says stop.** A 429 was being retried twice more,
which is the one response where asking again turns a throttle into a blocked
address. It now shuts a gate for the session, and so does a consent or
bot-check page — which arrives as a 200 carrying HTML where a feed was asked
for, and used to read as a broken channel. Nothing retries into it, and the
status line says what happened rather than leaving a dashboard that has quietly
stopped refreshing looking like one where nothing was posted. ADR-017.

Retries narrow to the case that measurably recovers. A 5xx is retried once,
after `Retry-After` if the server said. A 404 is not retried at all.

**The extractor fallback is bounded.** ADR-013 asks the extractor to list a
channel whose feed will not answer, and the feed service answers 5xx often
enough that this fired constantly — a browser-page fetch per followed channel,
four at a time, before anyone had pressed a key. It now runs one channel at a
time with a pause between, for the first three only, and not at all once the
gate is shut. ADR-013 is amended.

**One invented visitor per session, not per request.** A fresh identifier on
every request reads, from one address, as a stream of brand-new anonymous
visitors that each arrive once and never return. That is a bot signature, and
it was buying a property the address already gave away: the service does not
need a cookie to link requests it can link by connection. ADR-018 supersedes
ADR-016.

**A picture waits for the cursor to stop.** The thumbnail fetch sat inside the
draw, and the draw runs on every keypress, so holding an arrow key sent a
request for every row it travelled past. And the widescreen address was asked
for first, which older videos answer 404 to — so scrolling an older channel
sent a guaranteed 404 per row, which is what scanning looks like. The size
every video has goes first; the widescreen one is a second ask, only once the
first picture is on screen. ADR-019.

**Feeds go two at a time with jitter**, and the extractor is given
`--sleep-requests`, which covers the ADR-013 fallback as well as search.

## What this cost

Stated plainly, because every one of these is a real loss.

**Speed, and this is the big one.** Halving the concurrency and spreading the
fetches roughly triples a refresh. Measured against a stub with a fixed feed
latency, not against the live service:

| followed channels | feed latency | before | after |
|---|---|---|---|
| 20 | 150ms | 0.76s | 2.68s |
| 20 | 300ms | 1.50s | 4.09s |
| 50 | 150ms | 1.96s | 6.72s |
| 50 | 300ms | 3.91s | 10.78s |

A fifty-channel launch on a slow day now takes about eleven seconds where it
took four. When feeds are failing, the bounded fallback adds up to another
three to six on top. This is the change most likely to be regretted, and the
number to watch.

**Privacy, within a session.** Two searches and three videos in one sitting
can now be tied together by something bivy sends, where before each request
was a new stranger. The address already tied them together, so the loss is
small — but behind a VPN, where the exit address is shared, this identifier
becomes the thing that distinguishes one person's traffic. Nothing links one
session to the next: the identifier is invented at the first request, held in
memory, written only into the jars the extractor and the player read, and gone
when the process is. Feed fetches carry no cookie at all and never did.

**Channels past the fallback cap show as unreachable.** On a launch where more
than three feeds fail, the rest are reported unreachable rather than listed
through the extractor. They are not silently dropped: the dashboard names
them, and `LastVisit` is advanced only for channels that were actually
fetched, so their new videos are still new on the next successful launch
(`TestVisitedAdvancesOnlyTheChannelsThatWereFetched`).

**A 404 now fails on the first try.** The retry policy it replaced was written
around a measurement: the feed endpoint hands out 404s for channels that do
exist. Those channels now fail immediately and fall to the extractor fallback,
if they are inside the cap, and are reported unreachable if not. This is the
change most likely to be wrong, and it is a deliberate trade — retrying the
endpoint that just refused is what the release exists to stop.

**Pictures appear later.** A quarter of a second after the cursor stops, and
the better picture arrives after the adequate one rather than instead of it.

**None of this hides the address.** No program can, and bivy does not pretend
to. For that, run it behind a VPN; the README says so now. PLAN.md §2 has
always put IP-level exposure out of scope.

## What did not change, despite appearances

**The dashboard already used RSS.** `internal/feed` has always fetched
`feeds/videos.xml?channel_id=`, parsed it with `encoding/xml`, and sent no
cookie. There was no migration to make and none was made, so the limits people
associate with RSS are not new costs of this release: a channel feed carries a
bounded number of recent entries and no durations, and a channel that posts
more than the feed holds between two visits has rolled the older ones off
before bivy sees them. That was true in 0.1.0 and is true now.

**No cache, and no new directory.** Pictures still live in memory for the
session (ADR-007). The visitor identifier reaches only the two temporary jars,
which are removed with the process, so the isolation test's write set is
unchanged.

**ADR-004 is untouched.** No account, no API key, no browser cookie jar.

## What was checked

| check | result |
|---|---|
| `make check` | green — lint, vet, race, budgets |
| the race detector over the new goroutine and gate | green |
| the pacing, cap and gate tests, mutation-checked | fail when the guards are removed |
| the debounce test, mutation-checked | fails when the wait is removed |
| the prose compiler, `docs_test.go` | green across the six moved cookie claims |

The mutation checks are worth naming: the cap, the pause, the gate and the
debounce were each disabled in turn and the tests that claim them were
confirmed to fail. A pacing test that passes whether or not the pacing is there
is the failure mode this class of change invites.

## What was not checked

This is the half that matters, and for this release it is unusually large.

- **Nothing was run against the live service.** Not one request. The gate has
  never been seen to trip on a real refusal, the pacing has never been measured
  against a real feed endpoint, and the extractor's `--sleep-requests` has not
  been observed taking effect. Everything above is the suite and a stub.
- **The challenge strings are written, not measured.** `pushback.Detect` looks
  for phrases a refusal is expected to contain. They were reasoned from the
  shape of the error text, not captured from a live challenge. If the service
  words it differently the gate will not trip, and bivy will behave as it did
  before this release. This is the single weakest link in the change.
- **The block that prompted this has not been confirmed lifted**, and could
  not be attributed to bivy with certainty in the first place. The reasoning is
  that these three patterns are ones bot detection scores; that they were *the*
  cause is not established.
- **`make check` was run on one platform only**, not on Linux and not in CI.
  PLAN.md §11 asks for both.
- **No playback by hand this release.** ADR-015 already says stream resolution
  cannot be covered by CI.
- **The speed table is a stub with a fixed latency**, not a real feed endpoint.
  The shape is right; the absolute numbers are not a measurement of the live
  service.
- **Nothing was tested at scale.** The fifty-channel numbers come from a timing
  harness, not from anyone following fifty channels.
- **No security review by anyone outside this project.**

## Known outstanding

- **The gate cannot be reopened without restarting bivy.** That is deliberate
  (ADR-017): a gate that reopens is a retry loop with a longer period. It is
  still the sharpest edge in the release, and one false positive costs a
  session.
- **The User-Agent decision is open.** ADR-020 is proposed, not accepted: it
  weighs whether `internal/feed` should stop naming bivy, which matters on a
  shared VPN exit where the address no longer distinguishes anyone. The
  recommendation is to keep it. Nothing in the code changed.
- The 404 policy may need revisiting if channels start disappearing from
  dashboards; it is the reversal most likely to be wrong.
- Search still holds the loop for as long as the extractor takes.
- macOS has still never been launched by hand (PLAN.md §12).
- PLAN.md §13 still lists the open decisions.
