# 0.1.4

The release that makes playback work again, by sending one cookie bivy makes
up and keeps nothing.

## What changed since 0.1.3

**A new visitor for every request (ADR-016).** The service began refusing an
extractor that carried no visitor cookie, with the message "Sign in to confirm
you're not a bot". The message is misleading and that is the whole finding.
Four interleaved trials of each condition, against a video being refused:

| what was sent | result |
|---|---|
| no cookies | refused, every time |
| an empty cookie jar | refused, every time |
| a fabricated `SID` — the account cookie | refused, every time |
| a random `VISITOR_INFO1_LIVE` | resolved, every time |

An account does not satisfy it; an invented visitor does. So what is demanded
is a handle to count requests by, not a person to identify as — and the thing
bivy refuses to have was never the thing being asked for.

bivy now invents one per request and discards it after. That rotation is the
point rather than the cookie: left alone, a jar accumulates. Within seconds of
a first request the service had written `__Secure-YNID` into it — 348 opaque
characters, six-month expiry, readable only by them. A file that starts as a
random number becomes a durable pseudonymous identity that a viewing history
accrues to. Replacing it before every video and writing a fresh one for every
search is what prevents that.

**The status line keeps the cause and drops advice bivy will not take.** A
refusal used to arrive with the extractor's suggestion to pass `--cookies`
attached, which bivy does not do and which pushed the actual reason off the
end of the line.

## What was checked

| check | result |
|---|---|
| `make check` on Linux and macOS, in CI | green |
| `make dist-reproducible` | two builds, byte-identical |
| playback by hand, against the live service | played to its end, `end-file eof` |
| the same video through plain `yt-dlp` | refused |
| search, against the live service | results returned |

Those last three rows are the release. They were run with **no machine-level
extractor configuration at all** — the setup used during investigation was
removed first, so nothing outside bivy could be doing the work. The same video
that plain `yt-dlp` is refused on plays to its end under bivy, on a jar bivy
wrote and threw away.

Every test of the new behaviour was checked by mutation: with the per-video
rewrite removed, two videos in a session go out under the same identifier and a
cookie planted between them survives into the next. Both tests fail, which is
what makes them worth having.

## What was not checked

- **Nobody has launched bivy on macOS.** The suite and the scheduled
  integration run both execute there; no person has started the program on a
  Mac. PLAN.md §12 asks for that pass and it is still outstanding.
- **Stream resolution is not covered by CI and cannot be** (ADR-015). Hosted
  runners are challenged and the remedy on offer is an account, which ADR-004
  refuses. The most-used path in the program is verified by hand and by
  nothing else.
- **Thumbnails have no automated test that draws pixels**, and none has been
  seen on macOS by anyone. On the machine where they were confirmed by eye, the
  terminal does not answer the cell-size query at all, so bivy is drawing at an
  assumed cell size.
- **No security review by anyone outside this project.**
- **Nothing has been tested at scale** — a handful of followed channels.
- **The archives are not signed** (ADR-014).

## Known outstanding

- What this release works around is someone else's anti-bot measure, and they
  get a vote. A new visitor on every request also looks more like a bot than a
  returning one does; that trade is deliberate and recorded in ADR-016. When it
  stops working, bivy reports what the service said rather than "loading
  failed".
- Playback from inside a container still needs the host's mpv on the PATH.
  bivy does nothing about this automatically and whether it should is
  undecided.
- PLAN.md §13 still lists the open decisions.
