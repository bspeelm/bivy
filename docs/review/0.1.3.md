# 0.1.3

The first release with changes to the program rather than to how it is built.

## What changed since 0.1.2

- **`m` marks a row watched, or unmarks it.** The tick bivy sets itself means
  one thing — played to its end — and that is not the only way to be done with
  a video. The same key takes the mark back, and it is written to disk either
  way. `m` was "load thirty more", which is now `M`.
- **`:watched` hides the videos you have watched**, and shows them again. It
  applies to every list: the dashboard, a search, a channel you have opened.
  For the session only.
- **bivy says why a video would not play.** It was reporting mpv's
  `file_error` — a category, not a reason; "loading failed" is what mpv says
  whether the service refused, the network went, or the file was never a video
  — while holding the extractor's own message on a channel it already
  subscribes to.
- **An mpv that exits on its own is closed**, so its socket directory goes
  with it. Closing a video by its window left one behind per video, which is
  outside the two-directory write set §8 claims.

## What was checked

| check | result |
|---|---|
| `make check` on Linux and macOS, in CI | green |
| the scheduled integration workflow, both platforms | green |
| `make dist-reproducible` | two builds, byte-identical |
| playback by hand, against the live service | a real video played to its end, `end-file eof` |
| quitting with a video playing, on a live desktop | bivy exited, no mpv left on the host, socket directory removed |

That last row is worth naming. The failure it guards against — a killed mpv
outliving bivy and leaving windows on a desktop — has had a passing test since
it was fixed, and this is the first time anyone has watched it happen for
real, along with the two other ways playback ends: a video reaching its end
(mpv stays, idle, and serves the next one) and a window being closed (mpv
exits, and the next play starts a fresh one).

The message the new error handling produces was verified against the live
service refusing a real video, not only against a fixture — and that mattered,
because the first fixture had the wrong shape and the trimming it was supposed
to exercise never ran.

## What was not checked

- **Stream resolution is not covered by CI, and cannot be** (ADR-015). Hosted
  runners are challenged and the remedy on offer is a cookie, which ADR-004
  refuses.
- **Nobody has launched bivy on macOS.** The suite and the integration tests
  run there; no person has started the program on a Mac. PLAN.md §12 asks for
  that pass and it is still outstanding.
- **Thumbnails have no automated test that draws pixels**, and none has been
  seen on macOS by anyone.
- **Whether a terminal answers the cell-size query through a multiplexer is
  unknown.**
- **No security review by anyone outside this project.**
- **Nothing has been tested at scale** — a handful of followed channels.
- **The archives are not signed** (ADR-014).

## Known outstanding

- YouTube now requires a proof-of-origin token for many videos. Where it does,
  the extractor is refused and playback fails — which this release finally
  reports in words rather than as "loading failed". Nothing in bivy fixes
  that: it is resolved by configuring the extractor with a token provider,
  which needs no account and no cookies and so leaves ADR-004 standing.
- Playback from inside a container needs the host's mpv.
- PLAN.md §13 still lists the open decisions.
