# 0.1.5

Nothing in the program changed. What changed is that something is now watching
the things that rot on their own, and the first thing it found was five of
them.

## What changed since 0.1.4

**A weekly look at what has moved upstream.** bivy pins three kinds of thing
that do not announce themselves — the modules, the Go version `go.mod` names,
and the actions its workflows run — and nothing was watching any of them. A
job now asks, on Mondays, and opens or updates one tracking issue.

It reports and never acts. The Go line is what `scripts/dist.sh` pins
`GOTOOLCHAIN` to, so it decides what a published tag rebuilds into — and that
rebuild is what stands in for not signing the archives (ADR-014). A bot that
bumped it would quietly be changing the answer to the one question that offer
exists to answer.

mpv and the extractor are deliberately not in it. They are floors rather than
pins, and what breaks with them is behaviour rather than version, which the
scheduled integration run already exercises against the live service daily.

**The five things it found, taken:**

| what | from | to |
|---|---|---|
| `golang.org/x/term` | v0.27.0 | v0.46.0 |
| `golang.org/x/sys` | v0.28.0 | v0.48.0 |
| `actions/checkout` | v4 | v7 |
| `actions/setup-go` | v5 | v7 |
| Go toolchain | go1.25.0 | go1.26.8 |

`x/term` is the only direct dependency there is, and it was nineteen releases
behind. The two actions had been printing a Node 20 deprecation warning on
every run since the first release, and nobody was reading the annotations.

**The check was wrong about the toolchain, and was corrected.** It compared the
pinned Go against the newest Go there is, which is the wrong question: that
line is also the module's minimum, so chasing every major raises the floor
under everyone building from source. It now asks whether there is a newer patch
in the pinned line, and separately whether that line has fallen out of Go's
two-supported-lines window.

## What was checked

| check | result |
|---|---|
| `make check` on Linux and macOS, in CI | green |
| `make dist-reproducible` on the new toolchain pin | two builds, byte-identical |
| playback by hand, against the live service | played to its end, `end-file eof` |
| the corrected toolchain comparison, against the live release feed | three inputs, three correct answers |
| the weekly check, end to end | found five, closed its own issue when they were fixed |

That last row is the one worth stating. The job ran, opened an issue listing
five stale pins, the pins were updated, and its next run closed the issue
because everything was current. The loop was observed rather than assumed.

The toolchain comparison was exercised on the real release feed rather than
reasoned about: the current pin reports nothing, a `.0` reports its patch, and
a line two majors back reports both the patch and the loss of support.

The Node 20 deprecation warning is gone — zero occurrences in the run log,
where every run the week before carried them.

## What was not checked

Unchanged from 0.1.4.

- **Nobody has launched bivy on macOS.** The suite and the scheduled
  integration run both execute there; no person has started the program on a
  Mac. PLAN.md §12 asks for that pass and it is still outstanding.
- **Stream resolution is not covered by CI and cannot be** (ADR-015).
- **Thumbnails have no automated test that draws pixels**, and on the machine
  where they were confirmed by eye the terminal does not answer the cell-size
  query, so they are drawn at an assumed cell size.
- **No security review by anyone outside this project.** The dependency bump
  in this release was taken because it was current, not because anybody read
  the diff.
- **Nothing has been tested at scale** — a handful of followed channels.
- **The archives are not signed** (ADR-014).

## Known outstanding

- Playback from inside a container still needs the host's mpv on the PATH.
